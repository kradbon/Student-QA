
# Student Q&A Platform — Logical Database Model

## 1. Назначение

Логическая модель базы данных проекта Student Q&A Platform описывает структуру хранения данных для платформы вопросов и ответов студентов.

Система позволяет:
- Регистрировать пользователей с ролями Student, Moderator и Admin.
- Создавать и публиковать вопросы.
- Добавлять ответы на вопросы.
- Голосовать за ответы.
- Выбирать лучший ответ.
- Начислять репутационные баллы.
- Добавлять категории и теги.
- Загружать файлы к вопросам.
- Получать уведомления.
- Выполнять модерацию контента.

Модель не зависит от конкретной СУБД. В качестве целевой СУБД проекта рассматривается MySQL.

## 2. Список таблиц

| Таблица | Назначение | Ключи и связи |
|---|---|---|
| users | Пользователи системы | PK id; UQ username, email |
| categories | Категории вопросов | PK id; UQ name |
| questions | Вопросы пользователей | PK id; FK user_id → users; FK category_id → categories |
| answers | Ответы на вопросы | PK id; FK question_id → questions; FK user_id → users |
| accepted_answers | Выбранные лучшие ответы | PK/FK question_id → questions; UQ/FK answer_id → answers |
| tags | Справочник тегов | PK id; UQ name |
| question_tags | Связь вопросов и тегов | Составной PK (question_id, tag_id); FK на questions и tags |
| votes | Голоса за ответы | PK id; FK user_id → users; FK answer_id → answers; UQ (user_id, answer_id) |
| reputation_transactions | История изменения репутации | PK id; FK user_id → users; FK answer_id → answers (NULL) |
| attachments | Файлы вопросов | PK id; FK question_id → questions |
| notifications | Уведомления пользователей | PK id; FK user_id → users |
| moderation_logs | История действий модераторов | PK id; FK moderator_id → users; FK question_id → questions |

## 3. Типы связей

### 3.1. Один ко многим (1:N)

1. Один пользователь может создать много вопросов.
   `users → questions`

2. Одна категория может содержать много вопросов.
   `categories → questions`

3. Один вопрос может иметь много ответов.
   `questions → answers`

4. Один пользователь может написать много ответов.
   `users → answers`

5. Один пользователь может проголосовать за разные ответы.
   `users → votes`

6. Один ответ может получить много голосов.
   `answers → votes`

7. Один пользователь может получить много записей о репутации.
   `users → reputation_transactions`

8. Один пользователь может получить много уведомлений.
   `users → notifications`

### 3.2. Один к одному (1:1, необязательная связь)

Таблица `accepted_answers` хранит выбранный лучший ответ для вопроса.

- Один вопрос может иметь ноль или один выбранный лучший ответ.
- Один ответ может быть выбран лучшим только для одного вопроса.
- `question_id` является PK и FK.
- `answer_id` является FK с ограничением UNIQUE.

### 3.3. Многие ко многим (M:N)

Вопросы могут иметь несколько тегов, и один тег может использоваться в нескольких вопросах.

Для реализации используется связующая таблица `question_tags`:

- `question_id` → questions.id
- `tag_id` → tags.id
- Составной первичный ключ: `(question_id, tag_id)`.

## 4. Правила целостности данных

1. Каждый пользователь должен иметь уникальные username и email.
2. Каждый вопрос должен принадлежать существующему пользователю.
3. Каждый вопрос должен иметь существующую категорию.
4. Ответ не может существовать без связанного вопроса и автора.
5. Пользователь не может голосовать за один ответ более одного раза.
6. Автор ответа не может голосовать за собственный ответ.
7. Лучший ответ должен принадлежать тому же вопросу, для которого он выбран. Это дополнительно проверяется приложением.
8. Для одного вопроса допускается только один лучший ответ.
9. Репутационные операции должны сохраняться в истории.
10. При выборе лучшего ответа репутационные баллы начисляются автору ответа, а не автору вопроса.
11. Изменение репутации и создание соответствующей транзакции должны выполняться в одной транзакции БД.
12. Удаление пользователя, имеющего вопросы или ответы, не должно приводить к потере истории. Предпочтительно использовать блокировку или мягкое удаление.
13. Голосование разрешено только для опубликованных вопросов и ответов.
14. Модератор может выполнять действия модерации, а обычный студент не может выполнять административные операции.
15. Файлы должны иметь допустимый тип и размер, проверяемые приложением.

## 5. Нормализация до третьей нормальной формы (3НФ)

Для демонстрации нормализации рассмотрим условную плоскую таблицу `qa_flat`, которая содержит сведения о вопросах и ответах.

### 5.1. Исходная плоская таблица

| question_id | question_title | author_username | category_name | answer_id | answer_text | answer_author |
|---|---|---|---|---|---|---|
| 1 | What is Laravel? | student_a | PHP | 101 | Laravel is a PHP framework | student_b |
| 1 | What is Laravel? | student_a | PHP | 102 | It uses MVC architecture | student_c |
| 2 | What is React? | student_c | Frontend | 103 | React is a JavaScript library | student_b |
| 3 | What is MySQL? | student_b | Database | 104 | MySQL is a relational DBMS | student_a |

В таблице повторяются данные вопросов, авторов и категорий. При увеличении количества ответов повторение данных будет расти.

### 5.2. Первая нормальная форма (1НФ)

Требования:
- Каждая ячейка содержит одно атомарное значение.
- Нет списков значений в одном поле.
- Каждая строка должна однозначно идентифицироваться первичным ключом.

В таблице `qa_flat` значения атомарны. Каждая строка содержит один вопрос и один ответ.

Так как один вопрос может иметь несколько ответов, используем составной первичный ключ:

`PK (question_id, answer_id)`

Функциональные зависимости:

- `(question_id, answer_id) → answer_text`
- `question_id → question_title, author_username, category_name`
- `answer_id → answer_text, answer_author`

Таблица находится в 1НФ, но содержит частичные зависимости от составного ключа.

### 5.3. Вторая нормальная форма (2НФ)

Требования:
- Таблица должна находиться в 1НФ.
- Каждый неключевой атрибут должен зависеть от всего первичного ключа, а не от его части.

В исходной таблице данные вопроса зависят только от `question_id`, а данные ответа — от `answer_id`.

Разделяем таблицу на две:

**questions (2НФ)**

| question_id (PK) | question_title | author_username | category_name |
|---|---|---|---|
| 1 | What is Laravel? | student_a | PHP |
| 2 | What is React? | student_c | Frontend |
| 3 | What is MySQL? | student_b | Database |

**answers (2НФ)**

| answer_id (PK) | question_id (FK) | answer_text | answer_author |
|---|---|---|---|
| 101 | 1 | Laravel is a PHP framework | student_b |
| 102 | 1 | It uses MVC architecture | student_c |
| 103 | 2 | React is a JavaScript library | student_b |
| 104 | 3 | MySQL is a relational DBMS | student_a |

Теперь сведения об ответах и вопросах хранятся отдельно.

Однако в таблице `questions` остаются транзитивные зависимости, связанные с данными автора и категории.

### 5.4. Третья нормальная форма (3НФ)

Требования:
- Таблица должна находиться во 2НФ.
- Неключевые атрибуты не должны зависеть от других неключевых атрибутов.

В исходной модели существуют зависимости:

- `question_id → author_username`
- `author_username → user information`
- `question_id → category_name`
- `category_name → category information`

Чтобы устранить транзитивные зависимости, создаём отдельные таблицы `users` и `categories`.

Итоговая структура:

**users**

| id (PK) | username (UQ) |
|---|---|
| 1 | student_a |
| 2 | student_b |
| 3 | student_c |

**categories**

| id (PK) | name (UQ) |
|---|---|
| 1 | PHP |
| 2 | Frontend |
| 3 | Database |

**questions**

| id (PK) | title | user_id (FK) | category_id (FK) |
|---|---|---|---|
| 1 | What is Laravel? | 1 | 1 |
| 2 | What is React? | 3 | 2 |
| 3 | What is MySQL? | 2 | 3 |

**answers**

| id (PK) | question_id (FK) | user_id (FK) | body |
|---|---|---|---|
| 101 | 1 | 2 | Laravel is a PHP framework |
| 102 | 1 | 3 | It uses MVC architecture |
| 103 | 2 | 2 | React is a JavaScript library |
| 104 | 3 | 1 | MySQL is a relational DBMS |

Результат:
- Данные пользователя хранятся один раз в `users`.
- Названия категорий хранятся один раз в `categories`.
- Вопросы ссылаются на авторов и категории через внешние ключи.
- Ответы ссылаются на вопросы и авторов через внешние ключи.
- Повторение данных уменьшено.

Таким образом, структура соответствует требованиям 3НФ.

## 6. Итог

Логическая модель Student Q&A Platform включает таблицы пользователей, вопросов, ответов, категорий, тегов, голосов, репутации, вложений, уведомлений и модерации.

Связь M:N между вопросами и тегами реализована через `question_tags`. Связь 1:1 для лучшего ответа реализована через `accepted_answers`.

Нормализация до 3НФ позволила разделить данные пользователей, категорий, вопросов и ответов, уменьшить избыточность и устранить основные аномалии обновления, вставки и удаления.
